# H3 W4A8 8GB隔离后端

## 发布边界

控制台提供`fl2va_w4a8_8gb`与`ref2va_w4a8_8gb`两个启动器。两者固定到8GB资源
后端，不能借用16/24GB预算，并使用与INT8
版本相同的H3网络拓扑、Qwen、Video/Audio VAE、V24调度器和用户两控制量；变化的是
DiT基础权重的数值格式与显存执行图：

- 200个主要线性层使用group-16 packed W4、FP8 scale与运行时INT8 activation；
- 非目标张量保持checkpoint声明的原始精度；
- 首遍生成最高720P×15秒；
- 720P×15秒的Ref2VA发布边界为一个参考素材；更多参考按真实packed-token预算拒绝；
- H3二次采样开放720P/1080P、1–15秒；1440P仍拒绝；
- Base/LoRA仍是任务级热开关，不是第五、第六份基础权重。

该权重是有损量化，不能声称与INT8画质等价。当前门证明执行、显存与接口合同；
W4A8相对INT8的主观质量仍以Human成片审核为准。

## LoRA兼容结论

现有`minimax_h3_turbo_v4_step600_ema.safetensors`无需为W4A8重新下载一份。其metadata
声明`base_model=MiniMax-H3`，518个tensor组成259对LoRA A/B，目标名称覆盖同一50层
H3拓扑。运行时在W4基础投影之后以独立低秩分支叠加delta，不把LoRA烘焙回4-bit
权重，因此：

- INT8与W4A8共用同一个LoRA文件；
- FL2VA与Ref2VA沿用已经发布的任务级LoRA开关；
- W4量化误差与LoRA蒸馏误差会共同存在，技术兼容不等于质量完全相同。

实际CUDA门已验证W4完整投影、三个QKV output slice以及LoRA开/关的切片结果与对应
完整计算一致。FL2VA和Ref2VA的W4+LoRA均完成了真实H264/AAC成片。

## 低显存执行机制

8GB后端的内部优化器不按提示词内容写场景分支。它使用真实width/height/frames、文本token、
参考条件token和packed-token总数求解最快可行图。8GB路线的主要约束为：

- compact full-context K/V；
- Query与输出投影chunk 4096；
- W4 MLP按2048 token切块，仍执行完整`fc1 → SwiGLU → fc2`；
- 长序列必要时使用一个W4 block device buffer；
- Video VAE按阶段独占GPU，并保留288空间tile与精确host temporal输出；
- 1080P二采按真实长度自动选择全画布或相位对齐的时间窗；15秒16:9使用4个
  全空间窗口，避免空间接缝，重叠计算比例约1.141；
- 硬8GB最终Video VAE解码将decoder尾部12个block逐块换入，并以8个时间tile
  为一批写入CPU输出，既守住显存上限，又避免逐tile调度造成的巨大速度损失；
- Ref2VA参考图/首尾帧编码保持FP16 VAE权重，MiniMax后验moment、采样与latent归一化
  仍保留FP32边界，避免旧路径把整套5.2GB VAE临时膨胀到FP32。

W4 output slicing与MLP chunk只重排同一量化算子和LoRA计算，不删层、不删token。
V24的Actual/Forecast和逐层Attention近似仍由用户的步数与加速力度独立决定。

## 16GB与32GB主机内存门（2026-08-30）

W4A8后端新增两种主机内存生命周期。两者保持相同权重、V24调度、7.25GiB CUDA
分配上限和输出数学；区别只在可用主机RAM的准入档位：

- Qwen按执行顺序读取50个层文件，每层复制到两层滚动Pinned窗口后立即对源文件执行
  `POSIX_FADV_DONTNEED`，避免14+GiB干净页缓存长期滞留；
- Video/Audio VAE与3D latent upscaler通过`safetensors assign=True`绑定文件映射，
  不再先保留checkpoint再复制一份module state；
- Qwen/条件编码到DiT之间建立8GB专属allocator phase boundary；长序列每个非末尾
  solver步释放无效CUDA slab；
- W4A8 Linux启动路径启用`expandable_segments:True`，消除不同形状的Qwen、DiT、
  Sparse KV和VAE工作区在7.25GiB硬预算内产生的不可用碎片；
- 正式断点落盘后先删除video/audio latent、forecast history与最后一次denoise的CUDA
  引用，再清allocator，保证下一任务不继承约3GiB活跃显存。

验证使用systemd leaf cgroup，不是软件估算：16GB档设置`MemoryMax=14G`，32GB档设置
`MemoryMax=28G`，两者均设置`MemorySwapMax=0`。完整任务为FL2VA W4 Base、
1280×736、362帧、5步、95加速。

| 主机档位 | 完整端到端 | 主机RAM峰值 | CUDA allocated/reserved峰值 | cgroup pressure/reclaim/OOM | MP4字节数 |
|---|---:|---:|---:|---:|---:|
| 16GB（14GiB可用） | 129.356秒 | 10.61GiB | 6.6130 / 6.7891GiB | 0 / 0 / 0 | 25,893,771 |
| 32GB（28GiB可用） | 127.344秒 | 10.61GiB | 6.6130 / 6.7891GiB | 0 / 0 / 0 | 25,893,771 |

两份MP4字节完全一致；16GB相对32GB慢约1.6%，属于该次运行波动量级，没有交换、
主机内存回收或容量导致的长等待。DiT采样阶段主要保持约87–97% GPU利用率、
400–446W；Video VAE阶段达到100%利用率、约463–491W。

在此基线上，32GB档继续使用多出的主机内存建立专用加速路径：DiT的12.49GiB
CPU主权重直接通过`cudaHostRegister`原地锁页，不再额外复制一份Pinned master；
显存规划器在7.25GiB硬预算内为逐层Block Offload启用双缓冲，使下一层的PCIe H2D
与当前层GPU计算重叠。Qwen仍按层流式读取，Video/Audio VAE仍不锁定整模型，因为
它们每个请求只搬运一次，锁页副本没有相称收益。该策略不会改变模型权重、采样轨迹、
Attention动作或V24质量调度。

同一720p×15秒、5步、95加速任务的新路径三次完整运行分别为124.245、124.665和
125.580秒，中位数124.665秒；相对旧32GB路径快1.021倍（耗时降低2.10%），相对
16GB路径快1.038倍（耗时降低3.63%）。旧32GB、双缓冲首轮和最终验收MP4的SHA-256
均为`d525dc62ba0bd965bf1467f0291b325e9b9730a1e268f31be6a58905c65ad0c7`。

最终验收在`MemoryMax=30G`、`MemoryHigh=24G`、`MemorySwapMax=0`的systemd leaf
cgroup内完成：主机内存峰值24.002GiB，任务后常驻17.220GiB，Swap/OOM/OOM-kill
均为0，因此仍给32GB主机保留约6GiB系统余量。最终125.580秒的分阶段耗时中，
Qwen文本编码13.195秒、DiT去噪73.578秒、Video VAE解码33.408秒、封装3.350秒；
可被主机锁页覆盖的权重搬运已经不是主要剩余瓶颈。继续提高32GB档的RAM占用不会带来
数量级收益，后续明显提速应针对DiT算子和Video VAE计算核，而不是扩大CPU缓存。

在页缓存生命周期修复前，同一360P×1秒、5步/95的烟测为23.794秒并把28GiB
cgroup顶满；修复后为17.613秒、峰值11.17GiB、pressure/reclaim均为0，速度提升
约1.35倍。完整证据保存在：

- `runtime/validation/w4a8_host_ram_20260830/ram16_720p15_expandable_segments/`
- `runtime/validation/w4a8_host_ram_20260830/ram32_720p15_release_path/`
- `runtime/validation/w4a8_host_ram_20260830/ram32_drop_pages/`
- `runtime/validation/w4a8_host_ram_20260830/ram32_accelerated_double_buffer_r2/`
- `runtime/validation/w4a8_host_ram_20260830/ram32_accelerated_profiled_r5/`

哈希验证。该转换是独立的实验性权重，仍受MiniMax H3 Community License约束。
