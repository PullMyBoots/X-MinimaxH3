# H3 两控制量联合加速调度器

状态：v1 启发式、v2 条件精确优化器和 v3 shape-aware 全局联合 DP 均已保留。v3 第二轮 CPU 评价的 14 个硬门全部通过；非零加速档位仍需 v3 自己的真实 RTX 4090 成片与 Human 连续播放标签后才能设为发布默认。

## 1. 对外契约

高级请求只需要两个推理控制量：

1. `sampling_steps`：总 σ 采样轨迹长度。Base 支持 8–20，LoRA 支持 4–8。
2. `acceleration`：0–100 连续加速档位。0 是全真实步、Dense Attention 端点；100 是当前内部安全包络允许的最小计算预算。

它不直接承诺完成秒数，也不是质量百分比。分辨率、帧数、条件媒体和机器状态都会影响墙钟时间；相同任务与热态下，档位越高，规划计算量单调不增。

以下旧字段只为历史任务和旧客户端解析保留，不出现在新版 Web/ComfyUI 高级界面：

- `actual_steps`
- `lora_steps`
- `attention_keep_ratio`
- `sparse_scope`

## 2. 内部优化问题

给定总轨迹 `N` 和加速档位 `a`，调度器先把 `a` 映射为归一化 DiT 计算预算，再从候选轨迹中选择风险最小的方案：

```text
minimize   forecast_risk + attention_risk
subject to estimated_compute <= budget(N, a)
           all internal quality constraints hold
```

一个方案同时决定：

- 哪些 σ 位置执行真实 DiT；
- 哪些位置执行已有预测器；
- 每个真实位置的 50 个 Transformer Block 分别使用 Dense、TopK 0.50、0.25、0.10 或 0.0625；
- 哪些因果层由请求内 Dense 探针触发局部恢复。

当前采用“整体预规划＋局部 Online 保护”，不是无边界在线搜索。预规划为每个非零档位预留总 Dense 计算量 0～2% 的请求内恢复预算；Online 层只能把高风险局部升级为更保守动作，不会擅自降低质量或改变用户指定总步数。

v3 不再用一个 100k Token 比例覆盖全部视频。它内置 Round215 的两个真实 RTX 4090 端点：34,871 与 100,163 packed tokens；每个端点都含七层带×五动作的完整 56-Head 实测毫秒与 Dense-teacher 误差。中间 shape 插值，越界任务明确标记 `workload_extrapolated`。原始工件 SHA-256 写入每个全局证书。该模型只用于分配预算，不伪装成端到端 ETA。

风险先验来自 Dense 中间态差异、历史人工审核和已拒绝路线。它不是最终视觉评分器；运行时探针和 Human 成片审核仍是证据链的一部分。

## 3. 不可关闭的质量约束

`acceleration` 只能缩小预算，不能关闭下列约束：

- 开局至少保留 25% Attention，开局因果层至少保留 50%；
- 因果交互层始终至少保留 10%；
- 连续预测最多两个 σ 位置；
- 两个连续预测后的因果恢复位置至少保留 25%；
- 最后三个真实 DiT 位置的末端细节层至少保留 25%；
- Round182 风格的在线 Dense 探针只在关键因果层比较请求内误差，并对高误差 Head 做局部恢复；
- 保护文本、条件、音频前缀，以及 Round86 已通过人工审核的时空 rail 和全局 anchor 结构。

因此“质量保护强度”不是第三个用户旋钮。若允许用户把这些保护调到零，同一个加速值将失去稳定语义，也会重新暴露已经出现过的自动门、物体跳变、音色漂移、末端模糊和边缘闪斑。

## 4. Base 与 LoRA

Base 可以在同一总轨迹内联合使用真实步、预测步和 Attention 动作。20 总步的最快轨迹下限保留 12 次真实计算。v1/v2 固定复用已反复审阅的 12/8 骨架：

```text
0, 1, 2, 3, 4, 6, 8, 11, 14, 17, 18, 19
```

v3 将位置也纳入有限 DP，但仍强制：开头 25% 轨迹为真实步、最后三步为真实步、连续预测不超过两步、真实步不少于总步数的 60%。因此 v3 可能在同一 12/8 数量下提出新的中段位置；这属于需要独立 Human 审核的新轨迹，不能借用旧骨架的质量标签。

LoRA 已经是蒸馏后的 4–8 步短轨迹。当前调度器对 LoRA 设置 `allow_forecast=False`：总步全部是真实 Turbo 步，加速档位只分配逐步逐层 Attention。这样不会把尚未通过音频和运动人工验收的 LoRA 预测路线偷偷加入生产请求。

## 5. 热服务执行

模型只装配一次。每个请求把物理动作表写入 request-local context；同一热会话可以连续处理不同总步数和不同加速档位，不重建 DiT、不重新加载权重，也不修改共享模块。未找到请求上下文、步或层时一律回退 Dense。

正式断点保存动作表；恢复时必须与原请求完全一致，禁止用另一个加速档位续跑同一条 latent 轨迹。

- Base 20 步最快端点保留 12/8 审核骨架；
- LoRA 不产生预测步；

- 每个 v2 计划携带动作路径、保守预算、最优目标和 Pareto 前沿摘要的 SHA-256 证书，独立重放可发现路径或证书篡改；
- 评价器同时检查有效性、效率、简洁性。2026-08-19 第一轮 v2 CPU 报告为 13 个硬门全部通过、1 个 Human 门待定；冷规划 p95 约 970 ms，热缓存 p95 约 0.0012 ms，完整计划约 11.3 KiB。
- v3 `h3_joint_v3_shape_aware_global_dp` 用一个 Pareto-pruned 有限 DP 联合求解真实/预测位置与七层带动作，不再先固定骨架；
- v3 每条计划携带完整动作路径、shape 成本模型哈希、预算和最优风险证书。第二轮 CPU 报告为 14 个硬门全部通过、1 个 Human 门待定；19 个代表计划全部可解，冷规划 p95 约 1.469 s，热缓存 p95 约 0.0016 ms，完整计划约 8.8 KiB；
- v2 已完成同一 1280×736×124、seed82303 关门任务的首轮 GPU 对照：`acceleration=75` 为 123.187 s，`100` 为 96.845 s。它证明 v2 可执行，但 75 档映射过保守、100 档仍未获得 Human 质量标签。

尚未完成：

- 非零档位的 RTX 4090 端到端耗时曲线；
- 多场景动作、声音、清晰度和参考遵循的 Human 标定；

在这些真实成片证据完成前，`acceleration=0` 是唯一可称为 Dense 参考端点的值；非零值是新调度器候选，不能只凭 CPU 测试宣称质量通过。

## 7. “形式化最优”的准确边界

v2 的证书只证明：在以下有限问题内部，所选 Attention 动作使校准的加性 Human 风险代理最小：

- 已选定的真实步/预测步骨架；
- Dense、TopK 0.50/0.25/0.10/0.0625 五种动作；
- 固定的结构保护下限；
- 每单元成本向上取整到 5 ms 后的保守预算；
- 当前加性风险表。

它不证明真实人类观感全局最优，也尚未证明真实步与预测步的位置全局最优。v2 先用保留的 v1 低成本模型选择真实步骨架，再对该骨架做条件精确优化。这一限制被写进 `formal_optimality_scope`，不能在论文或发布说明中省略。

5 ms 保守量化使 v2 在 20 步代表点比 v1 少使用约 0.95%～1.2% Dense 等效计算，因此 v2 第一轮是“可认证控制基线”，并非已经证明质量优于 v1。下一轮应比较：更细量化、可认证近似最优界、以及联合真实/预测步的资源约束最短路，不能只继续手调 TopK。

v3 扩大了形式化范围：在给定 `total_steps`、`acceleration`、shape 成本插值、硬保护轨和加性风险表后，同时枚举真实/预测位置与每个真实步的七层带动作，并重放完整 Pareto DP。为了让冷规划低于 1.5 秒，34k/100k 端点分别使用 200/1000 ms 向上量化；这最多约为一个 Dense 步的 2.5%，只会少用预算，不会超预算。

v3 仍不证明 Human 全局最优，原因有三：风险表只有少量 Human 正负证据；风险目前是加性代理；Online Dense 探针只能局部升级，不能撤销已经形成的错误轨迹。因此证书的准确主张是“对声明的有限代理问题全局最优”，不是“生成视频质量全局最优”。

## 8. 可执行评价契约

运行：

```bash
cd subprojects-main/main/release/serve
PYTHONDONTWRITEBYTECODE=1 python -m scripts.evaluate_joint_scheduler \
  --output runtime/calibration/joint_scheduler_evaluation/v3_round2_cpu.json
```

评价分三组，任何硬门失败都禁止进入 GPU 成片阶段：

1. 有效：Dense 恒等端点、预算、单调性、结构保护、证书重放、34k/100k shape 成本端点、历史 Human 正负证据完整性；
2. 高效：冷/热规划开销和显式 Online 恢复预算；
3. 简洁：对外恰好两个控制量、确定性版本化计划、可审计序列化体积。

当前策略自己的 Human 标签是独立非硬门，但在发布判定中保持 `pending_human_review`。自动清晰度、SSIM、FasterVQA 或 Tensor 误差都不能替代这一门。

## 9. V7～V12 当前研究主线（2026-08-19）

旧章节保留了 V1～V3 的演进背景；当前研究主线已经推进到下列冻结版本：

- V7：把 Round215 的 50 个物理层 Dense 差异作为风险先验；真实 720p×5s 为 96.050s；
- V8：加入 Round218 的 step×layer 相位风险，不改变用户接口；
- V9：加入请求内 Dense teacher 探针和不可超支 ledger，但重复观察用完恢复金，归档；
- V10：用形式化三相位×三层哨兵替代重复观察，9 次观察后至少保留声明的修复余额；
- V11：在 V10 上增加 task-relative phase growth，修正绝对 RMS 随 shape 漂移的问题。
- V12：自然触发仍有最高优先级；若最后一个哨兵结束仍无触发，则把尚未使用的恢复金精确
  分配给未来风险收益最大的稀疏单元，升级为 Dense，而不是让预算闲置。

V11 policy id 为 `h3_joint_v11_calibrated_growth_global_dp`，online guard id 为
`round221_calibrated_growth_budget_v1`。离线 DP、动作成本、风险表、12/8 轨迹和结构约束均与
V10 相同；它只允许运行时局部升级，不增加稀疏度。Round221 校准、正式评价和完整限制见
`docs/JOINT_SCHEDULER_EVALUATION_REVIEW.md`。

V11 当前 22 个门通过、0 失败、3 待定。所有硬门已通过；`pending_human_review` 是有意的，
因为尚无自然触发后的 Human 成片证据。没有该证据时不得把“探针运行了”表述成“在线修复
改善了质量”。

V12 policy id 为 `h3_joint_v12_reserve_rebate_global_dp`，online guard id 为
`round223_reserve_rebate_budget_v1`。离线计划与 V11 完全相同；条件返还问题只在最后哨兵
之后求解。由于每个候选升级都统一按一个 Dense-layer equivalent 收费，求解器按校准风险
下降排序取前 K，并在计划中写入 choice/model SHA-256。这只证明“给定当前加性风险代理与
等额成本时的条件最优”，不证明真实 Human 质量最优。

真实 RTX 4090 结果：720p×5.17s 为 96.778s，9 探针＋12 次返还升级，较 V11 增加
0.361s；720p×15.083s 为 397.402s，9 探针＋11 次返还升级，较 V11 增加 3.394s。两者
均无触发、无预算拒绝，分别只剩 0.153846 与 0.238095 个 Dense-layer equivalent。V12
评价器为 23 pass、0 fail、4 pending；全部硬门通过，Human 连续播放仍待定。

断点语义同时升级为 fail-closed：正式 checkpoint 现在保存并重放在线 ledger、逐层相位
baseline、触发状态和待执行恢复状态。恢复请求不得重置已经花掉的预算，也不得把后半程探针
误当成新的首相位 baseline；任何策略、预算、返还表或状态不匹配都会拒绝恢复。
